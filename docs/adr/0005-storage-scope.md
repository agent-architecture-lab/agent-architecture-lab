# ADR 0005. 지원서·평가·회고를 어디에 저장할지 정한다 (결정 필요)

## 맥락

설계 문서는 데이터베이스와 벡터 데이터베이스를 범위에서 제외한다. 지금 워크플로는 Discord 요청 하나를 받아 처리하고 끝나며, 실행 사이에 남는 상태가 없다.

통합 서비스가 목표로 하는 흐름에는 실행 사이에 남아야 하는 데이터가 있다.

| 흐름 | 저장이 필요한 이유 |
|---|---|
| 모집 개시 → 접수 → 일괄 평가 | 접수 기간 동안 지원서를 모아 두어야 한다 |
| 평가 → 운영진 승인 → 매칭 | 매칭은 승인된 지원자 전체를 한꺼번에 봐야 한다. 승인 대기 중 평가 결과를 보관해야 한다 |
| 회고 피드백 | "지난주 Try를 실행했는가"를 짚으려면 같은 스터디원의 이전 회고가 필요하다 |

## 선택지

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 저장하지 않음 | 일괄 평가는 운영진이 합성 샘플 파일을 입력으로 넘긴다. 회고는 이번 회고만 본다 | 현재 범위와 원칙 그대로. 비용 0 | "모집 → 접수"가 데모 수준에 머문다. 회고 이력 기능 없음 |
| B. S3에 JSON 저장 | `applications/`, `screening/`, `retros/` 접두사별 객체. 수명 주기 규칙으로 기간 후 자동 삭제 | 서버리스, 저렴, 운영 부담 적음. Step Functions와 연결 쉬움 | 조회·수정이 불편. 동시 수정 제어 없음. 범위 변경 합의 필요 |
| C. DynamoDB | 지원자·회고를 항목으로 저장 | 조회와 조건부 수정이 쉬움 | 설계 문서가 제외한 "데이터베이스"에 해당. 스키마 설계 비용 |

## 제안

스터디 기간에는 **A로 시작하고, 일괄 모집 흐름을 실제로 시연할 때 B를 도입**한다. 어느 쪽이든 다음은 지킨다.

- 저장 대상은 익명화·합성 데이터뿐이다.
- 저장 기간을 정하고 수명 주기 규칙으로 자동 삭제한다.
- 운영진 승인 대기는 Step Functions의 `waitForTaskToken`으로 구현하고, 승인 결과도 저장 대상에 포함한다.

## 결정해야 할 사람과 사항

- **리더**: 범위 변경(B 또는 C) 허용 여부, 비용 한도(AWS USD 10) 안에서 가능한지
- **팀**: 회고 이력 기능이 6주차 회고 피드백 에이전트의 필수 요구인지

## 결과

- A: 추가 인프라 없음. ADR 0001의 `/screen` 브랜치는 입력 파일 기반 일괄 처리로 정의한다.
- B: `infra/template.yaml`에 S3 버킷, 수명 주기 규칙, 최소 권한 정책을 추가한다. 비용 경보 기준을 다시 확인한다.
