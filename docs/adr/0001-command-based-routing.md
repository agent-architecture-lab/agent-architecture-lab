# ADR 0001. 슬래시 명령별로 워크플로를 분기한다

## 맥락

Study Community AI Assistant는 성격이 다른 요청을 함께 처리해야 한다.

| 요청 | 요청자 | 필요한 단계 |
|---|---|---|
| 모집 공고에 대한 질문 | 지원자 | FAQ |
| 접수된 지원서 평가와 매칭 | 운영진 | 스크리닝 → (운영진 승인) → 매칭 |
| 주간 회고에 대한 피드백 | 스터디원 | 회고 피드백 |

현재 Step Functions 상태 머신은 명령과 관계없이 스크리닝 → 매칭 → FAQ → 리플렉션을 순서대로 실행한다. 이 구조에서는 FAQ 질문 하나에도 스크리닝 단계가 실행되고, 앞 단계의 입력이 없어 실패하면 FAQ에 도달하지 못한다.

ingress Lambda는 이미 `request.command`에 슬래시 명령 이름을 담아 워크플로를 시작한다. 설계 문서는 "라우팅은 코드가 결정한다", "에이전트끼리 자율적으로 주고받는 루프는 두지 않는다"를 원칙으로 둔다.

## 결정

1. 상태 머신의 첫 상태를 `$.request.command` 값으로 분기하는 Choice 상태로 둔다.
2. 명령마다 필요한 단계만 정해진 순서로 실행하는 브랜치를 둔다.

   | 명령 | 브랜치 |
   |---|---|
   | `/faq` | FAQ → 결과 전달 |
   | `/screen` | 스크리닝 → 결과 전달 (매칭은 ADR 0005 결정 이후 별도 명령 또는 승인 대기로 연결) |
   | `/retro` | 회고 피드백 → 결과 전달 |

3. 등록되지 않은 명령은 어떤 에이전트도 실행하지 않고 실패 결과로 바로 결과 전달 단계에 보낸다.
4. 다음에 실행할 에이전트를 LLM이 고르게 하지 않는다. 한 요청 안에서 여러 에이전트가 필요한 경우(예: 지원서 평가 중 FAQ 규정 확인)는 해당 브랜치에 단계를 고정 순서로 추가한다.

## 검토한 대안

- **현재의 단일 선형 파이프라인 유지**: 모든 요청이 모든 단계를 지나므로 비용이 늘고, 앞 단계 실패가 무관한 요청까지 막는다.
- **LLM Supervisor가 다음 에이전트를 선택**: 요청 종류가 슬래시 명령으로 이미 구분되므로 분류에 LLM이 필요 없다. 호출 비용과 지연이 늘고, 설계 원칙(라우팅은 코드)과 충돌한다.
- **자연어 한 문장을 받아 의도를 분류하는 Router**: 자유 질문 채널을 열게 되면 다시 검토한다. 그때도 분류 결과는 범주형 라벨로 받고 분기는 코드가 한다.

## 결과

- `infra/template.yaml`의 상태 머신 정의를 Choice 상태와 명령별 브랜치로 바꿔야 한다.
- Discord에 명령을 등록할 때 명령 이름이 상태 머신의 분기 값과 같아야 한다. 명령 이름 목록을 한곳(예: `community_ops/commands.py`)에 두고 테스트로 일치를 확인한다.
- 명령별로 필요한 Lambda만 호출되므로 실행당 상태 전이 수와 비용이 줄어든다.
